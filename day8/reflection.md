# Day 8 Reflection

The most difficult concept in this course was designing a system that remains reliable when many users access it at the same time. Initially, it was easy to think about application features individually, but harder to understand how the frontend, API, database, cache, and background workers interact under heavy traffic. I overcame this by breaking the system into components, tracing requests step by step, and identifying what could go wrong at each stage. Learning about database transactions and concurrency also helped me understand why checking seat availability in the frontend is not enough to prevent double booking.

Based on the feedback and rubric review of my QuickNotes capstone, I would improve the architecture documentation and make its design decisions more explicit. I would strengthen the capacity estimates, explain the role of each component more clearly, and show how the system handles failures and conflicting requests. I would also test the API client more thoroughly and ensure that the implementation, documentation, and README describe the project consistently. These improvements would make the capstone easier to understand, evaluate, and extend.

Next, I want to learn more about PostgreSQL transactions and row locking, Redis caching, message queues, API security, and load testing. I would like to build a small backend that implements real reservations and test it with simultaneous requests to see how concurrency controls work in practice. This would help me move from documenting system designs to building and evaluating reliable applications.
